PROJECT TITLE
-------------
Design and Implementation of an Automated Online Event Registration
and Management System

ABSTRACT
--------
This project presents the design and implementation of an Online
Event Registration and Management System that allows users to
register for events through a web-based platform. The system enables
event organizers to create events, manage participant registrations,
and generate attendance reports. Participants can view available
events and complete registration online. The system is expected to
improve efficiency, reduce paperwork, and provide a convenient means
of managing event-planning related activities.

TECH STACK
----------
Layer           | Technology
----------------|------------------------------------------
Frontend        | React.js (Vite) + Tailwind CSS
Backend         | Node.js + Express.js
Database        | MongoDB (Mongoose ODM)
Authentication  | JWT (JSON Web Tokens) + bcryptjs
Email Service   | Nodemailer (confirmations, reminders, OTPs)
PDF Generation  | pdfkit (reports, tickets, certificates)
File Uploads    | Multer (event banners, profile photos)
Scheduling      | node-cron (reminder emails, auto-close events)
Charts          | Recharts (dashboard analytics)
Environment     | dotenv
Form Handling   | react-hook-form
Notifications   | react-hot-toast
Icons           | @heroicons/react
HTTP Client     | Axios

WHY THIS STACK?
---------------
- React + Vite: Fast build times, component reuse, modern hooks-
  based architecture ideal for dynamic event listings and forms.
- Node + Express: Lightweight, fast REST API development with a
  large ecosystem of middleware.
- MongoDB: Flexible document model suits event data which varies
  greatly — some events have tickets, some are free, some have
  capacity limits, others are open. No rigid schema needed.
- JWT: Stateless authentication suitable for a web platform where
  multiple user types (Admin, Organizer, Participant) need different
  access levels without session storage on the server.
- Nodemailer: Handles transactional emails (confirmations, OTPs,
  reminders) — critical for event management workflows.
- node-cron: Automates time-sensitive tasks like sending event
  reminder emails 24 hours before an event starts, or automatically
  closing registration when capacity is reached or deadline passes.

WHAT EACH FEATURE DOES
-----------------------

1. EVENT CREATION (Organizer/Admin)
   Organizers create events by filling a detailed form: event name,
   description, category, location (physical address or online link),
   date and time, registration deadline, maximum capacity, ticket
   price (or mark as Free), and upload a banner image. Once created,
   the event appears in the public event listing for participants to
   discover and register for.

2. EVENT LISTING (Public / Participants)
   A searchable, filterable catalogue of all upcoming and ongoing
   events. Participants can browse by category, date, location type
   (physical/virtual), and price (free/paid). Each event card shows
   the banner, title, date, location, available slots, and a
   Register button.

3. PARTICIPANT REGISTRATION
   Participants register for an event by filling a form: full name,
   email, phone number, and any custom fields set by the organizer.
   After submission, the system checks capacity, validates inputs,
   generates a unique Registration Code, and sends a confirmation
   email with a PDF ticket attachment. Registration is blocked when
   the event is full or the registration deadline has passed.

4. REGISTRATION MANAGEMENT (Organizer/Admin)
   Organizers can view the full list of participants registered for
   their event, search/filter by name or status, mark attendance
   (present/absent) on the event day, export the participant list
   as a PDF or CSV, and send bulk email messages to all registrants.

5. ATTENDANCE TRACKING
   On the event day, the organizer marks each participant as Present
   or Absent from the participant list. This updates the participant's
   attendance status in real time. Post-event, the organizer can
   generate an attendance summary report showing total registered,
   total present, total absent, and attendance percentage.

6. AUTOMATED EMAIL NOTIFICATIONS
   - Registration Confirmation: sent immediately after successful
     registration, includes Registration Code and PDF ticket.
   - Event Reminder: sent automatically 24 hours before event start
     via node-cron.
   - Capacity Alert: sent to organizer when an event reaches 80%
     and 100% capacity.
   - Event Cancellation Notice: sent to all registrants if event
     is cancelled.
   - Waitlist Notification: sent when a slot opens up and a
     waitlisted participant is moved to confirmed.

7. WAITLIST SYSTEM
   When an event reaches maximum capacity, new registrations are
   placed on a waitlist. If a confirmed participant cancels, the
   first waitlisted participant is automatically moved to confirmed
   status and receives a confirmation email.

8. ADMIN DASHBOARD
   Displays system-wide statistics: total events, total registrations,
   upcoming events today, events by category chart, monthly
   registration trend chart, and recent activity. Admin can manage
   all users, all events, view all registrations, and generate
   system-wide reports.

9. ORGANIZER DASHBOARD
   Displays the organizer's own events: total events created, total
   registrations across all their events, upcoming events, and
   average attendance rate. Quick links to create event, view
   registrations, and mark attendance.

10. PARTICIPANT DASHBOARD (My Events)
    Participants see their registered events: upcoming registrations
    with countdown timers, past events they attended, and their
    registration history. They can cancel a registration (before
    the cancellation deadline) and download their ticket PDF.

11. REPORTS AND ANALYTICS (Admin/Organizer)
    - Event Registration Report: participant list, registration dates,
      attendance status — exportable as PDF.
    - Attendance Summary: present vs absent breakdown per event.
    - System Overview Report: all events, registration counts, and
      revenue (for paid events) — Admin only.
    - Monthly trends: bar charts for registrations over time.

12. ROLE-BASED ACCESS CONTROL
    Three roles: Admin (full system access), Organizer (manage own
    events and registrations), Participant (register, view own
    events). Each role sees a different dashboard, sidebar, and has
    access to different API endpoints.

13. AUDIT LOGGING
    Every significant action (event created, registration submitted,
    attendance marked, event cancelled) is logged with the user's ID,
    IP address, action description, and timestamp. Admin can view
    the full audit trail.

HOW TO RUN THE PROJECT
----------------------

Prerequisites:
  - Node.js v18 or higher
  - MongoDB v6 or higher (local or MongoDB Atlas)
  - npm v9 or higher
  - Git

Step 1 — Clone or open the project folder:
  cd event-registration-system

Step 2 — Set up the backend:
  cd server
  npm install
  Copy .env.example to .env and fill in your values (see below)
  npm run dev   (starts with nodemon on port 5000)

Step 3 — Set up the frontend:
  cd ../client
  npm install
  npm run dev   (starts Vite dev server on port 5173)

Step 4 — Open browser:
  http://localhost:5173

Step 5 — Login with seeded credentials:
  Admin       : admin@events.com       / Admin@1234
  Organizer   : organizer@events.com   / Org@1234
  Participant : participant@events.com / Part@1234

BACKEND API ROUTES
================================================================

AUTH — /api/auth
  POST  /register         Participant self-registration
  POST  /login            Login (all roles), returns JWT
  POST  /logout           Client-side token clear
  POST  /forgot-password  Send password reset email
  POST  /reset-password/:token  Reset password
  GET   /verify-email/:token    Verify email (optional)
  GET   /me               Get current user profile

CATEGORIES — /api/categories
  POST  /               Create (Admin only)
  GET   /               All categories (public)
  PUT   /:id            Update (Admin only)
  DELETE /:id           Delete if no events (Admin only)

EVENTS — /api/events
  POST  /               Create event (Admin, Organizer)
  GET   /               Public event listing (paginated, searchable,
                        filterable — only Published events for guests)
  GET   /my-events      Organizer's own events (all statuses)
  GET   /admin/all      All events, all statuses (Admin only)
  GET   /:id            Single event full details (public)
  PUT   /:id            Update event (owner or Admin)
  POST  /:id/publish    Publish event (owner or Admin)
  POST  /:id/cancel     Cancel event with reason (owner or Admin)
  POST  /:id/complete   Mark event as completed (owner or Admin)
  POST  /:id/banner     Upload banner image (Multer)
  DELETE /:id           Soft delete — Admin only

REGISTRATIONS — /api/registrations
  POST  /               Register for an event (Participant, Admin)
  GET   /               All registrations — Admin only (paginated)
  GET   /event/:eventId All registrations for an event (owner/Admin)
  GET   /my             Current user's registrations (Participant)
  GET   /:id            Single registration details
  POST  /:id/cancel     Cancel registration (owner or Admin)
  POST  /:id/attendance Mark attendance (Organizer, Admin)
  POST  /event/:eventId/bulk-attendance  Mark multiple at once
  POST  /event/:eventId/send-bulk-email  Send email to all registrants
  GET   /:id/ticket     Get ticket PDF download
  GET   /event/:eventId/export  Export participant list as PDF or CSV

WAITLIST — /api/waitlist
  POST  /event/:eventId  Join waitlist for a full event
  GET   /event/:eventId  Get waitlist for event (Organizer/Admin)
  DELETE /:id            Remove from waitlist

USERS — /api/users (Admin only)
  POST  /               Create staff/organizer user
  GET   /               All users (paginated)
  GET   /:id            Single user
  PUT   /:id            Update user / toggle active
  DELETE /:id           Deactivate

REPORTS — /api/reports

AUTOMATED SYSTEMS
================================================================

REMINDER SCHEDULER (node-cron — runs every hour: '0 * * * *')
  For each published event where:
    startDate is in the next (reminderHoursBefore) hours
    AND reminder not yet sent (add reminderSent: Boolean to Event model)
  Send reminder email to all confirmed registrants:
    Subject: "Reminder: [Event Title] starts in 24 hours!"
    Body: event details, location/link, ticket code, organizer contact
  Mark event.reminderSent = true

AUTO-COMPLETE (runs daily at midnight: '0 0 * * *')
  Find all Published events where endDate < today
  Set status = 'Completed'

CAPACITY ALERTS (triggered on each new registration)
  After each confirmed registration:
    Calculate fill percentage = (currentRegistrations / maxCapacity) * 100
    If fill% >= 80 AND alert not yet sent:
      Send email to organizer: "Your event is 80% full"
      Set event.alert80Sent = true
    If fill% == 100:
      Send email to organizer: "Your event is now fully booked"
      Set event allowWaitlist check

WAITLIST PROMOTION (triggered on registration cancellation)
  When a confirmed registration is cancelled:
    Decrement event.currentRegistrations
    Check event.waitlist — find oldest entry (lowest position)
    If found:
      Create new Registration for that waitlist entry (status: Confirmed)
      Delete from Waitlist
      Send promotion email: "Great news! A spot opened up for [Event]"
      Attach new ticket PDF
      Increment event.currentRegistrations

================================================================
FINE-GRAINED BUSINESS RULES
================================================================

1.  Participant cannot register for the same event twice
2.  Registration blocked if event status is not 'Published'
3.  Registration blocked after registrationDeadline has passed
4.  Registration blocked if currentRegistrations >= maxCapacity
    AND allowWaitlist is false
5.  If maxCapacity reached AND allowWaitlist = true:
    put new registration on Waitlist instead
6.  Organizers can only edit/cancel their own events
7.  Organizer cannot register as participant for their own event
8.  Event cannot be published without title, description,
    category, date, time, location, and maxCapacity filled
9.  Cancelling an event sends email to ALL confirmed + waitlisted registrants
10. maxCapacity cannot be reduced below currentRegistrations on edit
11. Attendance marking only allowed on/after event startDate
12. Guest registration (no account) allowed if Settings.allowGuestRegistration
    Guest reg stores email only — no participant ObjectId
13. Search and filter use server-side 400ms debounced queries
14. All dates displayed as DD/MM/YYYY HH:MM format
15. All prices in NGN with comma separators (NGN 5,000.00)
16. Session expiry auto-redirects to /login with toast
17. Soft delete events — never hard delete
18. Cancelled events remain visible with "Cancelled" badge

DEFENSE NOTES
================================================================

Q: Why did you choose MongoDB for an event management system?
A: Event data is highly variable — some events are physical, some
virtual, some have custom registration fields, some have complex
capacity rules. MongoDB's flexible document model accommodates this
without requiring schema migrations every time a new event type is
introduced. It also naturally stores arrays like customFields and
tags directly on the event document.

Q: How does the waitlist system work?
A: When an event reaches maximum capacity, new registrants are
added to a separate Waitlist collection with their details and a
queue position. When a confirmed participant cancels, the
controller decrements the event's registration count, queries the
Waitlist for the oldest entry, creates a new confirmed Registration
for them, deletes the Waitlist entry, and triggers a promotional
email with their new ticket attached. This is handled automatically
without organizer intervention.

Q: How do automated reminder emails work?
A: A node-cron job runs every hour and queries the database for
published events whose startDate falls within the next
(reminderHoursBefore) hours — a value configurable in Settings.
For each such event not yet sent a reminder, it fetches all confirmed
registrations and dispatches individual reminder emails via
Nodemailer. A reminderSent flag on the event document prevents
duplicate sends.

Q: What is role-based access control and how is it used here?
A: Three roles exist: Admin, Organizer, Participant. The JWT payload
carries the user's role. Every protected backend route passes through
roleMiddleware which checks req.user.role. Additionally, for
event-modification routes, ownership middleware checks that
req.user._id matches the event's organizer field. On the frontend,
RoleRoute components and sidebar items are conditionally rendered by
role from AuthContext.

Q: How do you prevent a participant from registering for the same
event twice?
A: Before creating a registration, the controller queries the
Registration collection for an existing document where both
event = eventId AND email = submitted email (for guest registrations)
OR participant = req.user._id (for logged-in users). If found and
status is not Cancelled, a 409 Conflict error is returned:
"You are already registered for this event."

Q: How does the capacity bar work on event cards?
A: The frontend calculates fill percentage as
(currentRegistrations / maxCapacity) * 100. A Tailwind-styled
progress bar reflects this, changing color: green below 60%,
amber from 60-89%, red at 90%+. This percentage is also shown as
text (e.g. "45/100 slots filled") so users can see availability
at a glance.

Q: What happens when an event is cancelled by the organizer?
A: The organizer provides a cancellation reason in a ConfirmDialog.
The backend sets event.status = 'Cancelled' and stores the reason.
Then it queries all Registration documents for this event where
status = 'Confirmed' or 'Waitlisted', collects their emails, and
dispatches cancellation notice emails including the organizer's
reason. It also marks the event.currentRegistrations unchanged
for historical accuracy and logs an AuditLog entry.

Q: Why did you add a Guest Registration option?
A: Not all event participants will want to create a system account,
especially for one-off events. Guest registration allows anyone to
register by email without creating a profile, reducing friction and
increasing event participation rates. This is toggled in Settings
so the admin can disable it for platforms requiring verified accounts.

Q: How does the custom fields feature work?
A: Organizers can define additional registration form fields per event
by adding entries to the event's customFields array (field name, type,
required flag). When a participant opens the registration form,
the frontend dynamically renders these extra fields. Submitted values
are stored in the registration's customFieldValues array as
key-value pairs. This makes the system flexible for any event type
without hardcoded form fields.

Q: What was the most challenging part of this project?
A: The most complex part was the waitlist promotion flow, because it
requires atomic operations — decrementing registration count,
promoting the waitlisted entry, creating a new registration, and
sending the email — all as a single consistent operation. I handled
this using Mongoose transactions to ensure that if any step fails,
the entire operation rolls back, preventing inconsistent states like
a participant being deleted from the waitlist but not receiving
their confirmation email.
